Evidence-first workflows for AI coding agents.

Focused skills, executor / researcher / verifier / strategist roles, optional runtime guards, and repeatable checks for the work an agent is about to call complete.

Install

From the Claude Code plugin marketplace, pinned to a tag. main is a source tree, not a release. 

/plugin marketplace add shubhamsingh-cell/fleetcraft@v0.3.1
/plugin install fleetcraft@fleetcraft

Then, in a new session, run /fleetcraft:doctor to confirm the installed package is intact.

What runs in your shell

Eight hook scripts are registered. Only three can be turned off in plugin settings; the other five act on every matching event, and one of those can stop a turn from finishing.

If a hook misbehaves: the always-on hooks have no setting of their own. Stop all of them with claude plugin disable fleetcraft@fleetcraft, or remove the plugin with claude plugin uninstall fleetcraft@fleetcraft. Every hook runs python3 -B, so python3 (3.9 or newer) must be on your PATH; they import only the Python standard library. None of them imports a networking or process-spawning module or calls eval or exec; their output goes into your session, or to the marker files noted above. That was checked by reading the imports at the tagged commit, not by running a sandbox.

Source: hooks/hooks.json and the userConfig block of plugin.json at the tagged commit. Read SECURITY.md before enabling anything.

Or evaluate from source

Python 3.9+ and the Claude Code CLI are needed for the package checks. The core skills can also be read as plain Markdown. Inspect SECURITY.md before enabling hooks. 

git clone https://github.com/shubhamsingh-cell/fleetcraft.git
cd fleetcraft
python3 scripts/validate.py
python3 -m pytest tests/ -q
python3 scripts/build_plugin.py
python3 scripts/check_plugin_parity.py
claude --plugin-dir plugins/fleetcraft

Run /fleetcraft:doctor in that session. python3 -m unittest discover works in place of pytest. A local --plugin-dir session evaluates the source tree as it is now, which is not the same as the tagged package the marketplace serves. The legacy installer is still available for source-layout users (bash scripts/install.sh --dry-run); it preserves existing configuration and reports its destinations. Avoid loading the manual and plugin copies together.

Plugin commands use the fleetcraft: namespace. The four agent roles separate execution, source gathering, independent acceptance, and escalated strategy judgment. Model aliases come from the adopter's environment; a model's prose identity is not runtime evidence.

What makes the checks useful

  • A task has an explicit scope, owner, base revision and acceptance evidence.
  • A regression test must fail against the broken behavior before its passing result counts.
  • Specification compliance and build quality receive separate verdicts.
  • A failed, missing or timed-out check stays OPEN; it cannot silently become PASS.
  • Visual proof requires an actual render. Testimonials, statistics and logos need real sources.
  • Existing authorization is carried forward; a new tool or skill does not expand it.
  • Provider integrations are detected before use. Fleetcraft does not install service clients or configure credentials merely because a workflow mentions them.

These are protocol rules. Only the documented runtime decision or CI check is technical enforcement; instructions alone do not guarantee model compliance.

One source tree, one generated plugin

Author skills/, agents/, hooks/ and their support files. The sparse plugins/fleetcraft/ distribution is generated by scripts/build_plugin.py; scripts/check_plugin_parity.py rejects stale generated content. This keeps a reviewable source layout while making the plugin self-contained.

The evaluation harness separates corpus validation, observed skill selection, and behavioral expectations. We make no unsupported claim about superiority, token savings, general routing reliability, or output-quality uplift. Results describe the cases and environment actually measured.
